# 酒馆机制兼容契约 v2

状态：当前开发基线
适用产品：Narrative Roleplay Engine / 叙界
契约版本：2
兼容报告数据结构：`schemaVersion: 1`，`acceptance.contractVersion: 2`

## 1. 目标与非目标

本契约定义叙界如何接收、解释、组装和运行 SillyTavern 生态中的角色卡、世界书、Prompt 预设、轻前端声明及独立重前端。目标是让同一份社区资源在不修改原件的情况下，获得可解释、可审核、可回归的运行结果。

兼容的对象是**资源格式与可观察交互语义**，不是 SillyTavern、酒馆助手或小白 X 的完整宿主实现。资源作者没有声明、样例没有覆盖、自动化没有验证的行为，不得宣称“完全兼容”。

本契约中的“必须”“不得”是发布门禁；“应当”是默认实现，偏离时必须在兼容报告中说明；“可以”是可选能力。

## 2. 不可变边界

1. 社区原件只读。修复、重排和降级结果写入本地派生版本，不覆盖原件。
2. 角色卡、世界书、预设、立绘、存档、审核记录和密钥只保存在本地，不进入 Git 仓库。
3. 格式解析成功不等于运行时兼容；静态内容可保存不等于脚本获准执行。
4. 安全降级必须列出被改变或禁用的能力，不得静默吞掉模板、脚本、变量或交互。
5. 第三方 JavaScript 默认进入“本地探索”而非宿主执行：被识别为当前支持的沙箱候选且具备当前 SHA-256 内容哈希后，可在隔离沙箱中观察运行并写入本地审计；严格模式才要求人工审核。当前哈希被明确拒绝或撤销时必须立即阻断。
6. 脚本不得获得父页面 DOM、Cookie、localStorage、Provider 密钥或任意网络权限。无法隔离的 DOM、iframe、网络、宿主 API 和不可控递归必须阻断。
7. 独立重前端使用独立包、独立来源、独立审批和受控模型网关；不得以内联角色卡 HTML 的方式取得主工作台权限。
8. 原始模型思维链不是资源兼容数据，不显示、不持久化，也不进入记忆；可审阅的决策摘要必须引用事实证据。

## 3. 兼容判定模型

### 3.1 单项能力状态

兼容扫描器对每项能力给出以下状态：

| 状态 | 含义 | 组装行为 |
|---|---|---|
| `supported` | 已由原生或声明式运行时实现，并有固定样例验证 | 可直接组装 |
| `degraded` | 核心语义可保留，但存在明确差异 | 用户确认差异后组装 |
| `review` | 存在当前沙箱可承接的第三方脚本候选 | 本地探索模式可观察运行；严格模式必须逐条审核 |
| `missing` | 依赖未实现宿主能力或不可隔离权限 | 原能力不得启用；只有剥离该能力的安全派生版可在确认后组装 |

### 3.2 资源级验收结果

| 结果 | 触发条件 | 可保存 | 当前可组装/运行 |
|---|---|---:|---:|
| `full-mapping` | 全部能力为 `supported` | 是 | 是 |
| `safe-degradation` | 至少一项 `degraded`，且无 `review`/`missing` | 是 | 用户确认后是 |
| `review-required` | 至少一项 `review`，且无 `missing` | 是 | 本地探索模式是；严格模式完成精确脚本审批后是 |
| `blocked` | 至少一项 `missing` | 是 | 原件不可直接运行；可选择受控重前端，或在明确剥离全部阻断项后创建安全派生版 |

资源级结果描述的是**原资源运行时**，不能把“静态字段可导入”误报为原运行时兼容。`blocked` 的 `canRun: false` 必须保持不变；安全派生版是一份新的、本地只读来源可追溯的运行产物，不会把缺失能力改判为已支持。

当角色卡、世界书或 Prompt 的静态内容仍然可用，且组装器能确定性地删除全部 `missing` 能力时，可以提供安全派生路径。组装前必须列出每个禁用项及影响，要求用户确认当前指纹，并在剧本清单记录 `status: safe-derivative-local-observe` 或 `safe-derivative-approved`、`sourceRuntimeBlocked: true` 与完整 `disabledCapabilities`。如果被删除能力承载资源的核心玩法或完整界面，产品应引导用户选择重前端通道，而不是把安全派生版描述成等价运行。

安全派生记录在创建后仍必须可见：会话健康检查应读取当前剧本清单，展示契约版本、禁用能力及影响；对话工作区必须提供直达该检查的入口。若清单声称源运行时被阻断，却缺少安全派生确认或精确 `disabledCapabilities`，健康检查必须标为异常，而不是继续显示“完全兼容”。

兼容扫描结果中的 `canRun: true` 只表示“原资源存在受支持的直接运行路径”，不代表待审核脚本已经获准。剧本组装必须再次读取 `compatibilityReview`：

- `requiresScriptApproval: true` 时，本地探索模式必须记录当前组装指纹与脚本哈希；严格模式还必须逐条提交 `scriptId + contentHash` 批准；
- `requiresCompatibilityAcknowledgement: true` 时，必须提交当前组装指纹的差异确认；
- 选择资源、资源版本、基础剧本、脚本内容或兼容契约版本任一变化，旧指纹立即失效；
- 严格模式审批不完整时，服务端不得创建剧本包；本地探索模式仍须完成适用的兼容差异确认。

## 4. 输入资源契约

### 4.1 角色卡

支持输入：

- Character Card V2/V3 JSON；
- 含 V2/V3 元数据的 PNG；
- 标准角色字段、开场白、备用开场、示例对话、角色系统提示和历史后指令；
- 卡内世界书和扩展容器；
- 大文件分阶段上传及 PNG 立绘剥离保存。

角色卡是角色身份、性格、语言习惯、边界与开场事实的高权威来源。通用 Prompt 不得静默覆盖角色卡；冲突必须在组装报告中出现。

### 4.2 世界书

支持输入：

- SillyTavern 世界书 JSON；
- 本项目约定的 YAML/文本世界书；
- 主关键词、二级关键词、正则、常驻、优先级、插入顺序、深度和位置；
- `selectiveLogic` 的 `and_any`、`and_all`、`not_any`、`not_all`；
- 逐条 `scan_depth`、Trigger Probability、Inclusion Group、Group Weight、Prioritize Inclusion、Group Scoring；
- Include Names、全局/逐条大小写覆盖、全局/逐条 Match Whole Words，以及 `/pattern/flags` JavaScript 正则键；
- Minimum Activations、Max Depth、递归扫描与带数值层级的 `delay_until_recursion`；
- Character Filter 的角色名、标签与 Exclude 模式；
- Generation Type Triggers 的 `normal`、`continue`、`impersonate`、`swipe`、`regenerate`、`quiet`；
- Additional Matching Sources：Persona 描述、角色描述、角色性格、Character Note/Depth Prompt、场景与 Creator Notes；
- 按消息数计算的 `sticky`、`cooldown`、`delay`，并随会话分支与 Swipe 保存；
- 明确的地点、人物、势力、历法、经济和修行规则向结构化世界系统投影。

世界书是客观世界规则与事实边界的高权威来源。脚本化控制器无法声明式转换时，只保留可验证静态事实，不得臆造脚本已经产生的状态。

世界书原文体量与单轮上下文预算必须分开报告：原件及全部条目继续在本地版本化保存，运行时只按作者声明的常驻、优先级、插入顺序、关键词、正则、递归深度和当前场景动态选取。预算不足时必须在调试报告中列出截断与省略数量，不得把“素材库总 token”伪装成每轮都会注入，也不得为了降低显示数字而改写原世界书。

世界书激活状态不得回写原件。`scan_depth` 以消息数而不是对话轮数计数，0 只允许递归触发；扫描消息使用 `\x01` 分隔，Include Names 开启时写入实际参与者名称。Minimum Activations 只逐步扩大聊天消息扫描窗口，不把上一轮递归内容混入额外扫描；逐条 `scan_depth` 覆盖仍保持固定，继承全局深度的条目才随扫描窗口扩大。`delay_until_recursion: true` 等价于层级 1，数值条目按从小到大的递归层级依次放行。纯文本单词键才应用 Match Whole Words，带 `/pattern/flags` 的正则键由自身 flags 决定大小写。

同一 Inclusion Group 同次扫描只保留一个候选，Prioritize Inclusion 优先于权重选择；sticky 生效期间不重复进行概率检查，sticky 结束后才进入 cooldown，delay 在已有消息数不足时阻断。概率与权重选择使用会话、分支和当前消息派生的稳定种子，以保持相同存档重放结果一致；它保留概率与权重语义，但不承诺复现 SillyTavern 进程内 `Math.random()` 的具体序列。考虑中文、日文没有稳定空格分词，本项目会话默认关闭 Match Whole Words，但完整保留全局设置与逐条覆盖。

Character Filter 在存在名称与标签两组包含条件时必须同时满足；Exclude 模式命中任一名称或标签即排除。名称按当前激活角色身份匹配，群聊指定发言人时只使用该发言人，未指定时使用本轮启用的角色集合。Generation Type Triggers 为空时适用于全部生成类型；非空时只在真实请求类型命中时激活，群聊重生成沿用 `normal`。Additional Matching Sources 只扩展当前条目的扫描缓冲，不会作为世界书正文注入 Prompt；逐条开关彼此独立，`scan_depth: 0` 不得仅靠这些附加来源直接激活。

SillyTavern 的 Character Filter 标签保存用户级 Tag ID，而 ID→名称的 `tags` 注册表及角色→Tag ID 的 `tag_map` 属于用户设置，不是普通世界书文件的自包含字段。导入器在资源同时携带 `tags`、`tag_registry`、`tagRegistry` 或设置容器中的标签对象时，必须保留原 ID 并生成可移植名称映射；对象内直接包含 `id + name` 时同样视为可恢复映射。只有 UUID/哈希形态 ID、没有名称且注册表无法解析时，才判为 `degraded`，不得把普通中文或自然语言标签名误报为私有 ID。未解析项必须在剧本组装结束前列出条目名与 ID 并要求用户确认；包含过滤条目保持不激活，排除过滤不得伪称已经可靠命中。社区原件不被改写，映射、差异清单和确认只写入本地派生资源及当前组装指纹审计。

组装器必须允许为当前选中的异常世界书配对独立 SillyTavern `settings.json` Sidecar，也必须提供无 Sidecar 时的人工 ID→名称映射。浏览器只提取 `tags` 中的 ID 与名称，不得把 Provider、密钥或其他用户设置发送给服务端。匹配结果以 `tag-registry-mapping` 类型写入本地世界书 revision，保留原 ID、记录恢复出的名称并重新运行组装预检；Sidecar 中没有命中的标签不得制造空映射或伪报修复成功。

### 4.3 Prompt 预设

支持输入：

- SillyTavern Prompt 预设 JSON；
- Prompt 模块的启用状态、消息角色、相对顺序、插入位置和历史深度；
- 配套安全正则和声明式扩展；
- 生成参数作为 Provider 建议值保存。

预设负责表达叙事流程、输出协议和文风，不得改写角色卡身份或世界书客观规则。Provider 参数不得在没有用户操作的情况下覆盖当前会话配置。

## 5. 机制映射契约

| 酒馆生态机制 | v2 映射 | 约束 |
|---|---|---|
| 标准角色字段 | 原生角色卡 | 保留字段来源与版本 |
| 世界书关键词/Depth/Position | 原生检索、动态预算与 Prompt 插入 | 四种二级关键词逻辑必须回归；常驻条目按作者优先级与插入顺序取舍 |
| 世界书概率/分组/时效 | 确定性激活器与 Swipe 状态快照 | `scan_depth`、概率、分组互斥、sticky/cooldown/delay 必须走真实 Prompt 调用链；预算淘汰项不得启动新时效 |
| 世界书扫描覆盖/递归层级 | 带参与者边界的扫描缓冲与分层状态机 | Include Names、大小写、Whole Words、Minimum Activations 和 `delay_until_recursion` 必须保留全局默认与逐条覆盖 |
| 世界书角色/请求过滤与附加来源 | 生成入口上下文 + 逐条扫描上下文 | Character Filter、六种 Trigger 值与六类 Additional Matching Sources 必须进入真实 normal/continue/regenerate 调用链；附加来源不得作为正文注入 |
| Prompt order/role/depth | Prompt 装配器 | 顺序可检查，不静默重排 |
| `{{char}}`、`{{user}}` 等登记宏 | 原生宏引擎 | 未识别宏原样保留并报告 |
| 显示正则 | 安全正则运行时 | 只改显示副本，不污染原消息与记忆 |
| Prompt 正则 | 受限 Prompt 变换 | 必须受作用域、深度和预算限制 |
| Quick Reply 文案 | 原生推荐行动 | 不把按钮脚本当普通消息执行 |
| `/setvar`、`/incvar` | MVU 白名单 patch | 未知命令禁用并报告 |
| MVU 初始状态 | 版本化 JSON 状态 | 禁止原型链键与越权路径 |
| `onImport`/`onUser`/`onAssistant` | 有预算声明式生命周期 | 任一步失败时整次事件回滚 |
| 安全 EJS 子集 | 只读插值与条件 | 赋值、循环、函数调用和任意代码禁用 |
| 状态/关系面板 | 原生侧栏卡片 | 不保留 DOM 事件和表单副作用 |
| 酒馆助手/小白 X 声明字段 | 部分声明式适配 | 未映射 hooks 必须列为差异或缺失 |
| Regex replacement 中的脚本候选 | 哈希绑定脚本沙箱 | 组装前逐条审批并审计 |
| 任意 extension hooks/宿主对象 | 不直接执行 | 未有专用适配器时为 `missing` |
| iframe/完整网页/WebView 应用 | `lra.heavy-frontend-pack/v1` | 不得以内联轻前端方式运行 |

“原生支持”只适用于表中已实现且有黄金样例断言的行为。字段被识别但没有实际进入 Prompt、状态、显示或动作调用链时，不得标记为 `supported`。

## 6. 第三方 JavaScript 审批契约

### 6.1 可进入审核的脚本

当前 v2 只承接已被正规化为 `regexTransforms[].requiresSandbox === true` 的 Regex replacement 脚本候选。普通 `javascript`、`hooks`、`onload`、父页面 DOM 操作或未知宿主 API 不会因为用户点击“批准”就自动变成可运行能力。

每条候选必须向用户展示：

- 脚本名称与来源资源；
- `scriptId`；
- 完整当前 `contentHash`；
- 作用域、匹配表达式和源代码；
- 风险等级与命中的风险项；
- 审核决定、备注、审核时间和策略版本。

### 6.2 审批时点

脚本风险、沙箱边界与当前内容哈希必须在自定义剧本向导的“校验确认”阶段可见，且早于剧本包创建；本地探索的首次运行与错误也必须进入同一审计链。不得运行若干轮对话后才首次披露风险或阻断项。

### 6.3 授权失效

以下任一事件必须让旧批准失效：

- 脚本内容、Regex、flags、作用域或深度变化；
- 资源 revision 变化；
- 用户撤销或拒绝；
- 脚本治理策略版本变化；
- 剧本重新组装产生不同兼容指纹。

### 6.4 隔离与审计

脚本 iframe 必须使用最小 sandbox 权限与 CSP：禁止网络、子 iframe、Worker、对象、表单和外部资源；脚本无法读取父页面 DOM、浏览器存储或 Provider 密钥。每次启动、加载、失败和阻断都写入本地审计，审计默认只记录元数据，不记录剧情正文。

## 7. 独立重前端契约

独立网页或 APK/WebView 不是轻前端脚本。网页包使用 `lra.heavy-frontend-pack/v1` 导入，并遵守：

1. 包文件按内容生成不可变版本和哈希；
2. 启动前展示当前版本的静态扫描与隔离边界；本地探索可启动并审计，严格模式才要求审核；
3. 在独立 `*.heavy.localhost` 来源运行；
4. 模型请求只能经过本地受控网关，前端永远拿不到真实 API Key；
5. 服务端强制 Provider、模型、并发、次数、输入字符和 Max Tokens 预算；
6. 浏览器存档留在独立来源；只有公开兼容接口时才生成托管快照；
7. 角色卡、世界书或预设中内嵌的 iframe 必须在普通资源通道判为 `blocked`；需要保留界面与行为时必须改走重前端导入，只保留静态角色扮演内容时可在列明删除项后创建安全派生版。

因此，黄金矩阵中的 `heavy-frontend` 行在普通角色扮演资源扫描器中预期为 `blocked`，这是对**原资源运行时**的正确判定，不代表重前端能力缺失。用户可以选择：

- 走独立重前端通道，保留网页交互和受控模型网关；
- 创建安全派生版，明确放弃 iframe、DOM、宿主 API 等阻断能力，只保留可验证的角色卡、世界书和 Prompt 静态语义。

两条路径不得混称。重前端运行能力由独立运行时测试验收；安全派生版由组装前删除清单、当前指纹确认和剧本清单审计验收。

## 8. 更新与版本契约

资源更新必须区分：

- **原件版本**：新下载内容，保持只读；
- **本地派生版本**：用户修复、适配或配置；
- **剧本引用版本**：当前故事实际绑定的 revision。

发现上游更新时可以提示，但不得自动覆盖正在使用的 revision。更新预览必须列出角色字段、世界书条目、Prompt 顺序、Regex、脚本哈希和审批失效范围。用户确认后创建新 revision；旧故事继续可复现，除非用户主动迁移。

### 8.1 历史剧本包兼容复审

缺少 v2 `compatibilityReview` 的历史自定义剧本包不得被静默补写为已审核。系统可以依据其资源清单与当前本地 revision 提供只读复审预览，但必须遵守：

1. 原资源、基础剧本或稳定来源信息缺失时停止自动复审，不臆造替代内容；
2. 预览列出来源包、当前资源 revision 变化、阻断能力、待审核脚本与新的组装指纹；
   对早于 revision 机制的历史素材，允许用剧本清单保存的来源内容指纹与当前素材指纹进行确定性比对：相同记为“指纹确认未变化”，不同记为“内容已变化”；只有 revision 与双方指纹都不足时才记为“无法确认”，不得把单纯缺少 revision 误报为内容未知；
3. 用户确认后始终创建新的 `custom-*` 派生包，并记录来源包、契约版本和 revision 变化，不覆盖历史包；
4. 已有剧本项目、会话和存档继续绑定历史包，只有用户后续显式迁移时才改变引用；
5. 不含脚本的复审可以从会话健康检查进入；存在第三方脚本时必须回到完整组装审核逐条核对 `scriptId + contentHash`，健康检查不得批量批准；
6. 复审只证明新派生包符合当前契约，不追认历史运行行为，也不改变原资源的 `blocked` 判定；
7. 素材库、剧本书架与内容包选择器必须共享同一份服务端兼容总览。未取得当前总览或缺少 v2 审计的历史包不得新建项目、新增会话卷或应用到其他会话；已有会话仍可继续阅读和对话，不得被自动迁移或改写。
8. 旧版本曾把一个酒馆预设的内部模块保存为多份顶层 Prompt 资源。复审预览必须按来源批次恢复为“一个预设包 + 有序内部模块”，明确列出折叠前后数量；用户确认后只为新派生包写入版本化预设包，保留模块顺序、启用状态、生成参数和运行伴侣，原分片、历史包与现有会话保持不变。

核心 18 单元之外，回归套件还必须保留以下护栏样例：

1. 未知 STscript 命令得到 `safe-degradation`；
2. 可沙箱 Regex JavaScript 得到 `review-required`，并在本地探索模式产生命中、启动与失败审计；
3. 普通 extension JavaScript、iframe 或宿主 DOM 依赖得到 `blocked`；
4. 脚本批准只匹配当前哈希，哈希变化、拒绝和撤销均阻断；

10. 缺少 v2 审计的历史包只能只读预检并创建新派生包；资源缺失时拒绝重建，含脚本时拒绝批量批准，现有项目和会话不得自动迁移；所有新开局入口和服务端写入口必须一致阻断。
11. 世界书逐条扫描深度、概率、分组优先级/权重、Group Scoring 和时效状态必须有固定测试；重生成不得重复追加当前用户消息，切换 Swipe 必须恢复对应激活快照。
12. 世界书名称边界、正则 flags、大小写/Whole Words 覆盖、Minimum Activations 的聊天专用扩深，以及 `delay_until_recursion` 数值层级必须有黄金测试。
13. Character Filter 的名称/标签包含与排除、Generation Type Triggers，以及六类 Additional Matching Sources 必须有导入、激活器、Prompt 装配和真实对话入口测试；`scan_depth: 0` 不得被附加来源绕过。

## 10. 新增兼容能力的发布门禁

任何新增“兼容”声明必须同时提交：

1. 脱敏结构样例；
2. 对应的资源类型、内容分级和交互复杂度；
3. 预期能力状态与资源级结果；
4. 实际调用链上的行为断言，而不只是解析断言；
5. 用户可见差异、阻断原因或审批信息；
6. 失败关闭测试，包括显式拒绝、撤销、越权和预算超限；严格模式下还必须覆盖未审核与哈希变化；
7. 相关专项测试、全量测试和仓库内容边界检查。

本地真实社区资源可用于 `npm run samples:audit`，但不得进入 Git；只有脱敏后的最小结构可以晋升为黄金样例。

## 12. 与 v1 的关系

[`tavern-compatibility-policy-v1.md`](tavern-compatibility-policy-v1.md) 保留为历史政策说明。v2 新增并收敛了：

- 四态资源级验收与单项能力状态的关系；
- 扫描可运行与脚本已授权之间的区别；
- 剧本组装前的指纹确认和逐脚本审批；
- 普通资源、轻前端脚本与独立重前端的强制分流；
- 原资源运行时阻断与安全派生组装的双轴判定及审计；
- 角色卡 / 世界书 / 预设 × SFW / NSFW × 文本 / 轻前端 / 重前端的 18 单元黄金矩阵；
- 上游更新、派生 revision 和审批失效规则。

自 v2 生效后，新兼容结论以本契约和黄金矩阵为准；v1 不再作为新增能力的验收依据。
