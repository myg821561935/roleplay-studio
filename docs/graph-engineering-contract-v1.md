# 剧情图谱工程契约 v1

本文定义叙界如何把现有剧情知识图谱从“可保存、可展示的关系数据”演进为“可提取、可融合、可验证、可检索、可回退的长期叙事事实层”。它约束领域语义和工程流程，不绑定 Neo4j、GraphRAG 框架或任何外部服务。

配套文档：

- `docs/knowledge-graph-v1.md`：当前存储、节点、关系和 API 实现；
- `docs/memory-system-v1.md`：分层记忆、摘要、向量召回和 CoT 边界；
- `docs/tavern-compatibility-contract-v2.md`：角色卡、世界书、预设和扩展资源的兼容契约。

## 1. 目标与非目标

### 1.1 目标

剧情图谱必须能够回答并解释以下问题：

1. 当前场景有哪些人物、势力、地点、物品、任务和事件与用户问题相关？
2. 两个人物为何认识、信任、敌对或从属于同一势力？
3. 某项事实来自角色卡、世界书、用户确认、正文事件还是模型推测？
4. 一次编辑、重生成或 Swipe 切换后，废弃分支形成的事实是否已经失效？
5. 当角色卡、世界书、正文提取和模型推测冲突时，哪一项可以进入 Prompt？
6. 图谱提供的关系是否可以追溯到具体资源或消息证据？

### 1.2 非目标

- 不保存、显示或还原模型原始 CoT；
- 不允许模型直接执行 SQL、Cypher 或任意图数据库命令；
- 不把向量相似度当成事实正确性；
- 不让图谱覆盖角色卡、世界书或用户明确确认的高权威事实；
- 不为了“使用图数据库”而立即迁移 Neo4j；
- 不把人物关系图 UI 当作事实源；
- 不把世界状态、事件账本、分层记忆和图谱建设成互相竞争的四套真相。

## 2. 总体流程

```text
角色卡 / 世界书 / 用户确认 / 正文 / 世界状态
  -> 资源和消息证据定位
  -> 实体抽取
  -> 关系与事件抽取
  -> Schema、domain/range、来源和证据校验
  -> 实体消歧与知识融合
  -> 冲突和权威裁决
  -> 图变更提案
  -> KnowledgeGraphService 审核提交
  -> SQLiteGraphRepository 持久化
  -> 按本轮问题检索场景相关子图
  -> Prompt / 关系图 / 导演审计视图
```

模型只能产生受约束的图变更提案。校验、融合、权威裁决、持久化和可见性过滤都由本地确定性代码完成。

## 3. 最小本体

v1 继续使用属性图模型。初始节点类型保持小而稳定：

| 类型 | 含义 | 典型唯一性依据 |
| --- | --- | --- |
| `Character` | 主角、NPC、群组角色 | 剧本作用域 + 规范名 + 明确别名 |
| `Faction` | 门派、组织、家族、机构 | 世界作用域 + 规范名 |
| `Location` | 场景、区域、世界地点 | 世界作用域 + 层级路径或规范名 |
| `Event` | 相遇、战斗、交易、结盟、背叛等已发生事件 | Session + 分支 + 证据消息 + 事件类型 |
| `Item` | 具有剧情意义的物品、资产或凭证 | 所属世界 + 规范名 + 必要时持有者 |
| `Quest` | 目标、委托、长期剧情任务 | Session + 稳定任务 ID |
| `Knowledge` | 秘密、线索、规则认知 | 内容指纹 + 来源 |

关系类型必须使用精确动词，不以泛化的 `RELATED_TO` 代替已知语义。现有关系继续兼容，但新提案优先使用：

- 人物关系：`INTERACTED_WITH`、`KNOWS`、`TRUSTS`、`HOSTILE_TO`、`OWES`；
- 组织关系：`MEMBER_OF`；
- 空间关系：`LOCATED_AT`；
- 事件关系：`WITNESSED`、`INVOLVED_IN`；
- 知识关系：`KNOWS_SECRET`。

每一种关系必须声明允许的 `sourceType -> targetType`。端点类型不合法的提案直接拒绝，不以降级成 `RELATED_TO` 的方式掩盖错误。

## 4. 实体身份与融合

### 4.1 身份键

`normalizeEntityName` 和稳定哈希只解决文本规范化，不等同于实体消歧。实体身份至少受以下作用域约束：

- 剧本/世界作用域；
- Session 与分支作用域；
- 实体类型；
- 规范名称和明确别名；
- 角色卡、世界书提供的稳定资源 ID；
- 已有关系、身份、地点和时间上下文。

### 4.2 合并规则

实体融合按以下顺序执行：

1. 相同稳定资源 ID：自动合并；
2. 相同规范名且相同类型、相同世界作用域：默认合并；
3. 命中资源声明的别名：自动合并并保留别名证据；
4. 仅有相似名称、称号或上下文推断：形成候选，不自动合并；
5. 存在身份冲突：拒绝合并，进入导演审阅。

每次合并必须保留原节点 ID、触发规则、证据和合并时间。拆分错误实体时可以恢复旧节点，而不是破坏性删除历史。

## 5. 事件与时间

动态剧情中的重要变化必须优先表达为 `Event` 节点，而不是把全部历史压缩成当前静态关系。

事件至少包含：

```json
{
  "eventType": "AllianceFormed",
  "title": "主角与青云门暂时结盟",
  "branchId": "main",
  "turn": 42,
  "sourceKind": "dialogue",
  "evidenceMessageIds": ["assistant-message-id"],
  "participants": ["character:...", "faction:..."],
  "locationId": "location:...",
  "confidence": 0.96,
  "visibility": "player"
}
```

关系边除 `validFromTurn`、`validToTurn` 外，还必须关联产生、确认或终止该关系的事件或证据。编辑、重生成、删除和 Swipe 切换触发分支重放时：

- 废弃分支产生的事件、关系和低权威节点标记为 `superseded`；
- 仍被角色卡、世界书或其他有效分支支持的实体不得误删；
- 依赖已失效事实的摘要、向量记录和图谱投影同时失效；
- 所有失效保留审计记录，不进行无痕物理删除。

## 6. 来源、证据与冲突裁决

沿用 `docs/knowledge-graph-v1.md` 的来源权威：

```text
role_card = world_book
  > user_confirmed
  > dialogue
  > world_state
  > migration
  > model_inference
```

每个进入有效图谱的节点、边和事件必须具有：

- `sourceKind`；
- `sourceId` 或 `evidenceSourceId`；
- 消息事实的 `evidenceMessageIds`；
- `authority` 和 `confidence`；
- `status`、`visibility` 与修订信息；
- 适用时的分支和有效回合。

冲突裁决规则：

1. 低权威信息不得覆盖高权威信息；
2. 同权威冲突保留双方证据，标记为待审阅，不任选其一；
3. 正文中明确发生的变化可以终止旧的动态状态，但不能改写静态角色身份和世界规则；
4. 模型推测只能进入 `candidate`，除非被用户确认或后续正文证据支持；
5. 玩家视图不得泄露 `director` 节点、边、事件或冲突详情。

## 7. 质量门禁

图变更提案提交前必须依次通过：

1. Schema 校验：类型、必填字段、状态、可见性和数值范围合法；
2. 端点校验：关系的 domain/range 合法且节点存在；
3. 证据校验：消息或资源定位存在，没有引用废弃分支；
4. 身份校验：实体融合规则已执行，没有未处理的高风险同名冲突；
5. 权威校验：没有低权威覆盖；
6. 时间校验：有效回合、分支和事件顺序自洽；
7. 隐私校验：导演信息不会进入玩家投影；
8. 幂等校验：重复处理同一证据不会产生重复节点、边或事件。

校验失败必须返回明确错误码和审计记录，不允许静默丢弃后伪装为成功。

## 8. 场景子图检索

Prompt 不应固定截取图谱数组的前若干条关系。检索输入至少包括：

- 当前用户输入；
- 当前角色和目标发言人；
- 当前地点、活跃任务和最近事件；
- 最近消息中出现的实体；
- 角色卡、世界书本轮激活条目；
- 玩家/导演视图。

候选子图按以下信号排序：

1. 当前输入和最近消息直接提及；
2. 当前地点、事件、角色和任务的一至两跳邻居；
3. 来源权威和证据完整度；
4. 当前分支及时间有效性；
5. 情节新近度；
6. 向量或关键词相关度。

默认只返回有证据、当前有效且玩家可见的两跳子图，并受独立 token 预算限制。向量检索用于寻找候选实体和事件，最终事实仍由图谱来源、证据和权威决定。

## 9. 与记忆和 Agent 的边界

- 世界状态保存当前可操作状态；
- 事件账本保存发生了什么；
- 剧情图谱保存实体、事件和关系的可查询结构；
- 分层记忆保存带证据的情节摘要；
- 向量索引负责从大量历史中寻找候选；
- Agent 使用经过过滤的上下文，不直接维护数据库。

正文生成保持单一叙事 Agent 的顺序主链。实体、关系、事件抽取可以作为回合后的后台步骤；只有相互独立的抽取任务才允许并行。融合、质量校验和提交必须由单一拥有者串行完成，避免多 Agent 竞争写入同一事实。

高风险操作设置人工门禁：

- 模型提议覆盖角色卡或世界书；
- 高置信度同名实体仍存在冲突；
- 第三方脚本请求图谱写入或外部网络访问；
- 批量合并、批量失效或资源版本迁移。

## 10. 存储演进边界

v1 继续使用 SQLite Repository。只有同时出现以下证据时才评估 Neo4j 或其他图数据库适配器：

- 单用户本地图规模或写入量已经形成可测性能瓶颈；
- 多跳、路径、社区发现等查询无法在当前实现中稳定满足延迟目标；
- 图谱需要多会话、多用户或远程服务并发访问；
- Repository 契约和迁移/回滚方案已经通过测试。

迁移存储不得改变节点 ID、来源权威、可见性、分支和证据语义。

## 11. 黄金验收用例

Graph Engineering v1 完成至少需要通过以下用例：

1. **别名融合**：角色卡声明“九渊/九渊仙尊”为同一人物，正文使用“师尊”后不产生三个 NPC；
2. **同名隔离**：不同世界或不同身份的同名人物不被自动合并；
3. **证据追溯**：任一正文关系可以定位到有效消息或资源条目；
4. **权威保护**：模型推测无法覆盖角色卡性格和世界书规则；
5. **分支失效**：重生成或 Swipe 后，废弃分支的结盟事件不再召回或显示；
6. **历史保留**：失效事实仍可在导演审计中查看；
7. **场景检索**：用户询问某人物时只注入相关两跳子图，而不是固定数组前 N 条；
8. **可见性隔离**：秘密和未揭示人物不会进入玩家 Prompt 或关系图；
9. **幂等重放**：同一 Session 重建两次后节点、边和事件数量稳定；
10. **存储可替换**：Repository 合约测试不依赖 SQLite 的实现细节。

## 12. 分阶段落地

### GE-1：契约与质量基线

- 固化本体、domain/range、身份作用域和错误码；
- 为现有快照、Repository 和 Prompt 投影补齐契约测试；
- 建立上述十项黄金用例的最小夹具。

### GE-2：融合与事件

- 增加实体候选、别名证据和可回退合并记录；
- 将正文关键变化抽取为事件节点；
- 将分支重放与图谱失效、记忆失效统一。

### GE-3：GraphRAG

- 按本轮问题、地点、角色、任务和事件检索两跳子图；
- 实施权威、时间、证据、可见性和 token 预算排序；
- 在调试视图记录查询输入、命中节点、裁剪原因和图谱修订号。

### GE-4：受控 Agent 工作流

- 将独立抽取步骤异步化或按需并行；
- 使用独立校验上下文复核提案；
- 所有融合和写入仍经过单一提交者与人工高风险门禁。

每一阶段都必须先通过相关测试；只有里程碑签发才运行完整回归和本地黄金资源矩阵。
